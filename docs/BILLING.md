# Billing catalogue and orders

Reference for the pack/order model (moved out of MASTER_PLAN §5, 2026-11-08). Business rules live in [POLICY.md](../POLICY.md).

- ~~Versioned catalogue (`billingFamilies → billingPlans → billingPlanVersions/benefits`) with an automatic discount engine.~~ **RETIRED 2026-09-29 [Hermes]:** replaced by the flat `packFamilies` + `packs` model. The `billingPlans`, `billingPlanVersions`, `billingPlanBenefits`, `billingDiscounts`, `billingDiscountEligibleStudents`, and `billingDiscountRedemptions` tables are still in the schema as **readable history only**; their documents were 0 in dev, and the tables (plus the `billingPlanSnapshot.familyKey/planKey` fields) are removed in a follow-up once a production readback confirms 0 rows. Nothing reads them.
- **Canonical model only:** `packFamilies` groups `packs`; a pack row carries its own name, lesson count, currency, price, optional sale price + end date, validity days, benefits, display order, and visibility. `pricing.createOrderRequest` writes the student’s pending order with an immutable price receipt; `pricing.createAdminOrder` does the same on a student’s behalf, optionally recording payment and granting immediately. Both paid paths share `grantBillingOrderCore` for the exactly-once grant, lesson-ledger provenance, finance record and notification. There is no package purchase path, gateway/webhook flow, compatibility adapter, versioning, draft/publish step, publication scope, price lock, automatic discount rule engine or allowlist.
- **Discount codes 2026-10-27 [Codex]:** admins create/copy/disable percentage codes above the catalogue, with optional expiry and total use limit. Students apply one code on billing; admins can also apply one while ordering on a student’s behalf. It discounts the current offered price (including sales) across available packs. Pending requests reserve a use atomically, rejection releases it, and granting preserves the price/code receipt in the order and lesson grant. Codes apply only to new requests; existing orders retain their agreed amounts. `discountCodes` is separate from the retired historical discount engine. No payment-policy change.
- **Clean manifest:** student order is Standard Tutoring then IELTS; each family is 4 / 8 / 12 lessons. Standard Tutoring is 15,000 / 26,000 / 36,000 KZT; IELTS is 20,000 / 35,000 / 48,000 KZT. Every pack starts its 60-day window on first lesson use and contains its four localized commercial benefits. Benefits never gate platform access.
- **Admin WhatsApp orders 2026-11-02 [Codex]:** Billing → Commercial catalogue & orders → **Order for a student** searches existing students, selects a visible pack/currency, applies a discount code and previews the receipt. Create an order awaiting payment or explicitly confirm payment to grant the pack immediately; actual received amount/currency/date and an inline USD equivalent when needed use the existing finance path. Existing pending orders are linked for completion rather than duplicated; request retries reserve discount capacity, grant lessons and record income once. Staff provenance is retained. After granting, a calendar link opens the assigned teacher; **Add lesson** books on the student’s behalf. Browser verification remains with FaFo.
- **Admin/student/public contract:** `/admin/billing` is one screen — families with ▲▼ ordering, packs under each family with an inline edit drawer (name, lessons, price, sale price, sale end, validity, benefits, visible) and a live preview of exactly what the student and the website render, then the order queue and a "give lessons by hand" box. `/student/billing` and the public website both read the same rows in the same order; a hidden or archived family/pack disappears from both, and a new family appears on the website without a code change. Both surfaces always render family, pack name, price/currency, lesson count, validity, and every configured benefit.
- **Pricing copy locales:** pack/family/benefit text is authored in `default` + English + Russian + Kazakh; Arabic retains its English fallback through `localizePricingText`. New and existing families/packs can be authored in Kazakh through the admin editor. Missing Kazakh fields on an independently created row still fall back to English. The message catalogues carry all four locales with exact key parity.
- **Website visibility per family:** `packFamilies.showOnWebsite` (default shown) keeps a family sellable inside the portal while leaving it off the public website. IELTS ships switched off, which preserves the delivered "three Standard offers on the site" behaviour that the retired `basic_tutoring` allowlist used to enforce. One checkbox in the family dialog; the family row shows `Website: shown/hidden`.
- **Release boundary:** the 2026-09-12 destructive reset was development/test only. A production data reset remains prohibited; the production cutover for this model is the additive deploy plus the confirmation-bound `pricingSeed:seedPricingCatalogue` run, which writes only `packFamilies` + `packs`.
- **Admin finance cleanup controls shipped 2026-09-29 [Hermes]:** Money Ledger now exposes the existing guarded finance-entry delete action. The order queue exposes `pricing.deleteOrphanedOrder` only for terminal orders whose buyer user no longer exists; pending orders and orders with a surviving buyer show a disabled explanation. The mutation deletes only the order and exact order-owned finance, grant/transaction, and billing-notification rows in one transaction. No production deletion was run; the post-deploy production readback remains 5 finance entries and 3 billing orders.
